## Why

MDH reaches Interactive Brokers only through the TWS API (`ibkr`, `ib_async`, socket to TWS or IB Gateway on port 4001/4002). That needs a running TWS/IB Gateway process with its own login, a free client id (error 326 on conflicts) and a long-lived socket. IBKR also offers the **Client Portal Web API**: a REST interface served locally by the Java **Client Portal Gateway (CPGW)** (`https://localhost:5000/v1/api`), authenticated once per day through the browser. It needs no client id, no socket and no `ib_async`, speaks plain HTTPS/JSON like the other HTTP providers of MDH, and delivers the same IBKR market data entitlements (they belong to the username, not to the API).

The new provider must deliver the **same functionality as `ibkr`**: last prices and history for stocks, ETFs, indices and front-month futures, option chains and option quotes with Greeks, underlying implied volatility, company profile and search, market-open status, entitlement errors and connection test. Where the Web API documentation lacks an equivalent (news, IV history, continuous futures series), the gap must be verified in a spike and answered explicitly (`CAPABILITY_NOT_SUPPORTED`, documented deviation), never with silent empty data.

Documentation: `https://www.interactivebrokers.com/docs/web-api/v1/introduction`, `https://www.interactivebrokers.com/docs/web-api/api-reference/` (Markdown versions via `.md` suffix, checked on 2026-11-19).

## What Changes

- **New provider `ibkrweb`** (`app/providers/ibkr_web.py`, display name "IBKR Web API (CPGW)"), implementing `BasePriceProvider`, `BaseOptionsProvider`, `BaseCompanyProvider` and `BaseVolatilityProvider` with the same instrument support sets as `ibkr` (prices and history: stock, etf, index, future; IV snapshot: stock, etf, index, future after spike verification; option underlyings: stock, etf) and the same native intervals (`1m`, `2m`, `5m`, `15m`, `30m`, `1h`, `1d`, `1w`). Disabled by default; `ibkr` (TWS API) stays unchanged and can still be used.
- **Parity contract**: a parity matrix in the spec maps every `ibkr` method to its Web API endpoints; a shared parity test suite runs the same response-shape assertions against both providers with recorded fixtures. Response models, canonical symbols, `source_instrument`, `option_id` format (OCC local symbol, e.g. `AAPL  261218C00200000`), IV units (decimal fractions, four places), error codes and `provider` field semantics are identical.
- **Session management for the CPGW**: two-tier session (read-only SSO session from the browser login, brokerage session via `POST /iserver/auth/ssodh/init`), state machine `unreachable` → `login_required` → `brokerage_pending` → `ready` (plus `competing`), 2-second wait and non-empty `GET /iserver/accounts` before the first `/iserver` request, keep-alive `POST /tickle` every 60 s in a background task, automatic re-initialisation after the nightly IServer reset (≈ 01:00 local region time), fail-fast while a login is required, optional alert webhook when the daily login expires.
- **Pacing**: client-side limiter below the documented global limit (default 6 of 10 requests per second, leaving 2 for order-hub on a shared gateway), an extra limiter for `/iserver/marketdata/history` (50 per minute), and a 15-minute penalty-box pause after any HTTP 429 instead of retrying.
- **Market data via snapshots**: pre-flight + polling of `/iserver/marketdata/snapshot` (500 ms update frequency), market data availability (field `6509`: `R`/`D`/`Z`/`Y`/`N`/`O`) mapped to the existing `market_data_type` semantics and to `PROVIDER_NOT_ENTITLED`, bounded number of open streams (`unsubscribeall` when the limit is reached), historical daily close fallback like `ibkr`.
- **Contract resolution and caching**: conids from `/iserver/secdef/search`, `/trsrv/stocks`, `/trsrv/futures`, `/iserver/secdef/strikes`, `/iserver/secdef/info`; resolved conids cached in process and in Redis (conids are stable for the lifetime of a contract).
- **Connection settings** in the encrypted provider config (`connection_config`): `base_url` (default `https://127.0.0.1:5000`), `verify_tls` (default `false`, the CPGW ships a self-signed certificate), `ca_bundle`, `account_id`, `compete` (default `false`), `market_data_type` (default `3`), `max_streams` (default 80). No credentials are stored in MDH; the login happens in the CPGW.
- **Admin UI**: `IbkrWebConnectionSection` with the connection fields, a live session panel (connected/authenticated/competing, live or paper, username, server version, time to expiry), "Open gateway login", "Initialise brokerage session", "Logout" and "Test connection"; capabilities chips for `ibkrweb`; warning that `ibkr` and `ibkrweb` with the same username compete for the one brokerage session.
- **Operations**: optional Docker Compose profile `cpgw` building the gateway from IBKR's official download (Java 17 JRE, `conf.yaml` with `ips.allow` for the compose network, port bound to `127.0.0.1` only); README section with the login procedure (local browser or SSH tunnel), daily re-login and the single-session rule.

## Capabilities

### New Capabilities
- `ibkr-web-provider`: Web API provider over the CPGW: registration, configuration, session lifecycle and keep-alive, pacing, contract resolution, prices and history, option chains and quotes, implied volatility, company data, market-open status, error mapping, parity contract with `ibkr`.
- `ibkr-web-connection-ui`: Admin UI section and admin endpoints for the CPGW connection and session.

### Modified Capabilities
- `provider-symbol-mapping`: translation table and futures semantics gain the `ibkrweb` column (conid resolution, front-month future also for history).
- `provider-capabilities-display`: capabilities of `ibkrweb`.
- `provider-connection-test`: `ibkrweb` tests the CPGW session instead of a socket.

## Impact

- **Code**: new `app/providers/ibkr_web.py` (plus `app/providers/ibkr_web_session.py` for session/keep-alive/pacing and `app/providers/ibkr_web_contracts.py` for conid resolution if the module grows beyond ~800 lines); shared helpers extracted from `app/providers/ibkr.py` without behaviour change (trading-hours parsing, futures exchange table, index root/exchange tables, OCC option symbol parsing); `app/providers/registry.py` (class map), `app/admin/provider_config_repository.py` (`KNOWN_PROVIDERS`, `CONNECTION_CONFIG_ALLOWLIST`, defaults), `app/api/routes_admin.py` (`PROVIDER_CAPABILITIES`, `IbkrWebGatewayUpdate`, session endpoints), `app/observability/metrics.py` (provider set, session state gauge), `app/config.py` (`IBKRWEB_*` settings), `app/main.py` (provider list), OpenAPI/MCP descriptions that list provider names, Admin UI (`IbkrWebConnectionSection`, routing in `ProvidersPage`/`DashboardPage`), `docker-compose.yml` (profile `cpgw`), `tools/cpgw/` (Dockerfile, `conf.yaml` template).
- **API**: additive; new provider name `ibkrweb` for every `provider` parameter that accepts `ibkr`. New admin endpoints `PUT /api/admin/providers/ibkrweb/gateway`, `GET /api/admin/providers/ibkrweb/session`, `POST /api/admin/providers/ibkrweb/session/init`, `POST /api/admin/providers/ibkrweb/session/logout`. Existing `ibkr` responses unchanged.
- **Dependencies**: none new (`httpx` is already used).
- **Costs**: none in MDH. Market data subscriptions are per username; a second IBKR username (to run TWS and the Web API in parallel) is billed separately by IBKR.
- **Clients**: VisioTrade and TradeSensei need no change when they use the system defaults; clients that pass `provider=ibkr` explicitly keep the TWS provider until they switch to `provider=ibkrweb`.
- **Not covered**: news (the Web API has no historical news endpoint; `ibkrweb` does not implement `BaseNewsProvider`), IV history unless the spike proves a documented or reliably working source, continuous futures history (expired contracts are not listed by `/trsrv/futures`), automated or headless CPGW login (not supported by IBKR), OAuth 1.0a/2.0 (only for institutional and third-party accounts), websocket streaming (`/ws` topic `smd`) and the MDH `/ws/prices` endpoint, orders, portfolio, scanners, alerts, watchlists, account management, migration of client calls from `ibkr` to `ibkrweb`.
